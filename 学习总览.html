PHASE 1 · 2026-09-08

阶段① 计算器：学会把需求说清楚

学习目标：不写一行代码，只靠描述，让 ZCode 生成一个能用的完整应用。这是和 AI 结对编程的第一课——它写得快不快取决于你说得清不清。

成果：calculator.html

四则运算 + 取余 连续运算（12 + 3 × 4） 表达式回显 + 结果大字显示 AC 清空 / ⌫ 退格 键盘直接输入（数字 / 运算符 / Enter / Esc） 除零报错提示，不崩页面 浮点精度处理（0.1+0.2 不出现长尾）

双击 calculator.html 即可在浏览器打开使用。

这一阶段学到的方法

  • 需求 = 布局 + 交互规则 + 边界情况。只说「做个计算器」，得到的是玩具；说清「支持连续运算、除以 0 要提示错误、小数结果保留合理精度」，得到的才是工具。
  • 先要最小版本，再追加要求。第一版出来后，继续提「支持键盘输入」「显示历史表达式」这样的增量需求，比一次性提完所有要求更容易得到好结果。
  • 验收就是自己用一遍。按需求清单逐条试，发现差距就具体地告诉 ZCode「哪里和预期不符」。
PHASE 2 · 2026-09-09

阶段② 台账调试：学会向 AI 报告问题

练习材料是一段「预期输出写在注释里、代码里藏着 bug」的 Python 统计脚本。任务是让 ZCode 找出问题并修复——这练的是真实工作里最高频的能力：清楚地报告一个 bug。

题目里的两处 bug（很好的对照样本）

显性 bug一运行就报错

ledger_stats.py:18 把 amount 拼成了 amout，一运行立刻抛出：

KeyError: 'amout'

报错信息带行号、带原因，直接贴给 ZCode 就能修。

隐性 bug能跑完但结果是错的

ledger_stats.py:21 在循环内部把 office_total 重置为 0，导致办公小计只等于最后一条办公记录（33.0），而不是 198.5。

办公类小计：33.00 元 ← 错
办公类小计：198.50 元 ← 对

显性 bug 等着你，隐性 bug 才考验人——它不报错，只有对照「预期输出」才能发现。

向 ZCode 报 bug 的黄金结构

这个练习形成的固定套路，09-22 在「导入导出」排查里（见问题档案）真的用上了：

  • 现象：实际发生了什么（报错原文 / 错误的输出值）
  • 预期：应该是什么（题目注释里写的预期输出就是现成的预期）
  • 复现：怎么触发（运行 python ledger_stats.py）

参考答案 ledger_stats_fixed.py（09-22 补）运行验证通过：总金额 1662.50、办公小计 198.50、平均单笔 277.08。原题文件保留 bug 状态，方便随时重练。

PHASE 4 · 2026-09-22 · 真实排障记录

问题档案：导入导出排查实录

09-22 用户报告两个现象：「导出的 json 无法正常打开」「导入之前导出的 json 显示数据为空」。这是第一次用自己的应用出了真问题、按阶段②的方法排查——结论：两件事都不是功能 bug，但都暴露了值得改进的地方。

排查三步（方法本身就是阶段②的套路）

步骤做了什么发现
① 查证据文件 用 Python 解析那份 09-14 导出的备份 JSON 文件是合法 JSON，但内容本身就是空的：items: []、tagBank: []——导出那一刻浏览器里就没有数据
② 走查导出代码 检查 exportBtn 的处理逻辑 导出读取的数组和列表显示的是同一个 items——只要列表里有数据，导出文件就一定有数据，代码没有会导出空文件的路径
③ 走查导入代码 检查 importFile 的处理逻辑 导入按设计「覆盖当前全部数据」——导入空备份 = 把列表清成空。确认框其实提示过「将导入 0 条待办」

两个现象的结论

「无法正常打开」

文件本身没问题（合法 JSON、UTF-8 编码）。最可能的两个原因：

· Windows 没给 .json 关联默认打开程序——双击弹出「你要如何打开这个文件」。右键文件 → 打开方式 → 选记事本 / VS Code / 浏览器，勾选「始终使用此应用」即可。

· 编辑器按 GBK（ANSI）解码——文件是 UTF-8 无 BOM，个别中文编辑器会把中文显示成乱码。用记事本（Win10 自带版）或 VS Code 打开都正常。

· 下载文件被安全设置拦截（09-24 验收时实证）：浏览器下载的文件带「来自 Internet」标记（MOTW），安全设置严格时双击会提示「Internet 安全设置已阻止打开此文件」。右键文件 → 属性 → 勾选「解除锁定」→ 确定即可。此拦截不影响应用导入（导入直接读取文件内容，不走该检查）。

「导入后数据为空」

那份备份导出时就是空的。为什么当时会导出空的？最可能：导出功能刚做完（15:16），六分钟后（15:22）在一个没有数据的浏览器环境里试了一下导出——比如另一个浏览器、或还没录入待办的新窗口。

⚠️ 如果后来在常用浏览器里确认导入了这份空备份，原有待办已被覆盖。localStorage 没有回收站，无法恢复——这正是热身卡要加固的第一件事。

背后值得记住的知识点：localStorage 按「源」隔离

浏览器里 localStorage 不是「一台电脑一个仓库」，而是每个浏览器 × 每个来源（origin）各一个独立仓库：

  • 双击打开 todo.html（来源是 file://）和通过本地服务打开（来源是 http://127.0.0.1）——两套完全独立的存储
  • Chrome 里的数据和 Edge 里的数据，互不相通；无痕窗口又是一套全新的

这解释了「为什么在这个窗口里有待办、换个窗口就没有」——数据没丢，只是去了另一个仓库。导入导出功能正是为了在这种时刻搬家用的。

延伸：localStorage 隔离的四个解决方向（按投入递增）

方案做法效果与代价
① 固定入口
零代码，立刻可用		 选定一个主力浏览器，永远用同一种方式打开（建议一直双击，并把 .html 的默认打开方式设成它） 数据固定在一个仓库里，困惑消失；换电脑 / 重装浏览器时仍要靠导出导入
② 用足导出
现有功能		 把「导出数据」当存档习惯，重要改动后顺手导出一份 零成本当保险；靠自觉，不适合当日常同步手段
③ 数据落到文件
File System Access API		 页面经授权后直接读写磁盘上一个 JSON 数据文件，替代 localStorage 数据跟着文件走，换浏览器也能接着用；仅 Chrome / Edge 支持，首次需选一次文件授权，复杂度中等——可作第 8 步后的进阶练习卡
④ 加个小后端
下一个学习项目候选		 用 Python 起一个小服务（Flask 几十行），数据存服务端，页面统一从 http://127.0.0.1 打开 数据只有一份、所有浏览器看到同一份——所有网站的真实工作方式；投入最大，但正好衔接八步完成后的新项目，用上阶段②的 Python 基础

推荐组合：现在用 ①+②（零成本解决 90% 的困惑）；八步练完把 ④ 当下一个项目（可与「记账本」合并为带后端的应用）；③ 看兴趣插入。隔离本身是浏览器的安全设计，无法直接「打通」——只能统一入口、把数据搬出浏览器、或手动搬运，以上四案分属这三条思路。

METHODS

心得与方法：沉淀的六条

1. 好需求 = 背景 + 目标 + 验收标准 + 约束

✗ 模糊的需求

「给待办加个搜索」
——搜什么？怎么触发？和筛选什么关系？全靠 AI 猜，返工率高。

✓ 清晰的需求

「加关键词搜索：输入即时过滤；匹配标题和简述；与状态、标签筛选叠加生效；无结果时给专门提示。」
——每一条都可直接验收。

第 5 步练习卡里的需求话术就是按这个结构写的，照着改造成自己的话即可。

2. 小步迭代，每步可验证

todo 项目八步走，每步只加一块能力、验收一次。比起「一口气做个完整应用」，小步的好处是：错了立刻知道错在哪一步，而且每一步的代码改动小到能看懂。

3. 让 ZCode 自己证明「能用」

口说无凭，跑起来算数：Python 脚本就运行看输出（阶段②），网页就开浏览器实际操作。验收动作本身可以让 ZCode 代劳——报错原文和实测结果，比「应该可以了」可信一百倍。09-22 的排障也是同一逻辑：先解析文件拿证据，再走查代码下结论。

4. 报 bug 的固定结构：现象 + 预期 + 复现

阶段②练出、阶段④实战的套路。特别注意隐性 bug：程序不报错但结果不对（比如空备份导入后列表悄悄变空），这时「预期行为」是唯一的裁判——所以写需求时顺手写清预期，将来就是验收依据。

5. 改数据前想着「另一边」

两个真实教训：① 改数据结构时想着旧数据——todo 项目从 tag 演进到 tags、新增字段，都靠 normalizeItem 平稳过渡；② 改数据内容前先备份——导入空备份会覆盖现有数据且无法恢复。AI 助手再聪明，也替你兜不住「没备份」。

6. 学习材料本身也要「持久化」，练习要亲手做

两个 09-22 的领悟：中断八天只能靠代码反推进度，所以有了这份总览——存档即进度；第 5 步被 ZCode 代做后发现「看完不等于学会」，所以转为练习卡模式——ZCode 负责示范方法和验收，动手的留给本人。
